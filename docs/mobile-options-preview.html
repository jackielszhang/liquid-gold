Liquid Gold

Android + iOS without killing the widget

A short map of your options. Home-screen widgets are the filter — not an afterthought.

See the paths

Starting point

You already have an iOS client

This repo is not a blank slate. That changes which path is smart.

  • SwiftUI app for region, fuel, and tank size.
  • WidgetKit home widget reading the same cached snapshot.
  • Shared JSON contract from the Python pipeline — already cross-platform friendly.

Decision filter

Widgets are first-class or you’re fighting the OS

A fill-now / wait answer lives on the home screen. Cross-platform UI kits help the app; they usually do not own the widget.

Refresh rules

iOS WidgetKit and Android App Widgets / Glance both limit how often you can update. Native APIs handle this cleanly.

Shared cache

App and widget must read the same snapshot (you already do this with an app group on iOS).

Web / PWA gap

Installed web apps do not give you real home-screen widgets like Liquid Gold needs — especially on iOS.

Options

Five paths, ranked by widget fit

Tap a path for pros, cons, and what the widget work actually looks like.

01 · strongest widgets

Native twin

Best fit for you Widget: excellent

Keep SwiftUI + WidgetKit. Add Kotlin / Jetpack Compose + Glance (or App Widgets) on Android. Share only the JSON + rules.

Pros

  • Best home-screen widgets on both platforms — no bridge tax.
  • You keep the iOS work you already shipped.
  • Data pipeline stays untouched; both apps fetch the same file.
  • UI can match each OS (Glance timelines, WidgetKit families).

Cons

  • Two UI codebases to maintain (Swift + Kotlin).
  • Design parity is manual — you reimplement screens, not share them.
  • Bug fixes can land on one platform before the other.
Widget reality Android Glance mirrors what you already do on iOS: fetch → cache → render recommendation. This is the path where “widget on the home screen” feels native, not bolted on.
02 · share logic, not UI

Kotlin Multiplatform

Widget: excellent Shared models

Rewrite shared parsing / recommendation logic in Kotlin Multiplatform. Keep native SwiftUI and Compose UIs + native widgets.

Pros

  • One place for JSON decode, stale rules, and snapshot building.
  • Widgets stay fully native on both sides.
  • Good long-term if Android becomes as important as iOS.

Cons

  • You already have Swift shared models — KMP means a rewrite of that layer.
  • More tooling / project setup than “just add Android.”
  • UI and widgets are still written twice.
Widget reality Same widget quality as native twin. You only share the brain, not the home-screen shell. Worth it if logic drift between platforms starts to hurt.
03 · one UI kit

Flutter

Widget: workable Rewrite app UI

One Dart UI for both phones. Home widgets still need native Android/iOS extensions (or community packages that wrap them).

Pros

  • Ship app screens once with strong visual control.
  • Large ecosystem; fast iteration on in-app UI.
  • Packages exist to talk to native home widgets.

Cons

  • Throws away your current SwiftUI app surface.
  • Widget is still a second, native-ish project — not “free” with Flutter.
  • Apollo Utility / LCD look needs careful Flutter theming to match.
Widget reality Possible, but the hard part (timeline refresh, app-group / shared prefs, small layouts) stays platform-native. Flutter helps the app more than the widget.
04 · JS team path

React Native / Expo

Widget: weak Config plugins

Cross-platform app UI in React. Home-screen widgets need custom native modules; Expo support is limited.

Pros

  • Familiar if your team lives in JS/TS.
  • Fine for settings screens and simple flows.
  • Can still hit the same JSON endpoint.

Cons

  • Home widgets are the pain point — exactly your priority.
  • Often means ejecting / writing Swift + Kotlin beside RN anyway.
  • You rewrite the iOS app you already have.
Widget reality Poor match for Liquid Gold. You’d build native widgets and a RN shell — more moving parts than native twin, worse widget story than Flutter or KMP.
05 · web install

PWA / TWA only

Widget: no Skip for v1

A website “Add to Home Screen.” Fast to prototype the idea — but not a real dual-platform widget product.

Pros

  • Fastest way to show the recommendation in a browser.
  • One deploy; pipeline already publishes JSON.
  • Useful as a temporary public page, not as the app.

Cons

  • No proper iOS home-screen widget.
  • Android web widgets are limited and inconsistent.
  • Fails your “widget on the home screen” requirement.
Widget reality Do not pick this if the home-screen widget is a product pillar. Keep the web for status pages; keep the product native.

Recommendation

Ship Android native next to iOS

Because the widget is the product surface, native twin is the least regretful move: keep LiquidGoldApple, add an Android app + Glance widget that consume the same fuel-data.json.

Revisit Kotlin Multiplatform later if shared Swift/Kotlin logic starts drifting. Skip RN/PWA for the client unless the widget requirement is dropped.

  1. 1 Mirror shared models + snapshot builder on Android.
  2. 2 Build the Glance home widget first (your real MVP).
  3. 3 Add the small settings app around it.
  4. 4 Only then consider KMP to dedupe logic.
